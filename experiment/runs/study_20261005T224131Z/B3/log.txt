#### 2. Deep-Dive Architectural Deconstruction

##### Why `branch_2` is Discarded (Architectural Failure Under Load)
`branch_2` implements a multi-pass reconciliation strategy:
1. Performs an event sweep to rebuild discrete temporal intervals.
2. Allocates intermediate interval data structures on the heap.
3. Iterates over those intervals a second time to intersect them with business calendar boundaries and tally business minutes.

**Fatal Architectural Flaws:**
* **Allocation Churn ($O(N)$ Intermediate State):** Reifying running intervals into memory structures creates continuous pressure on the garbage collector/allocator. Under real-world ticket event streams (hundreds of thousands of transitions across SLA lifecycles), this materializes an unbounded sequence of interval tuples.
* **Redundant Traversal:** It decouples interval reconstruction from metric aggregation. Traversing the event stream to construct ranges, only to re-traverse those ranges to apply business hours, doubles cache misses and destroys instruction pipeline locality.

##### Why `branch_1` Survives (The Production Standard)
`branch_1` utilizes an in-place per-ticket state machine driven by closed-form business-minute arithmetic.

**Architectural Strengths:**
* **Zero Intermediate Allocations ($O(1)$ Memory Footprint):** State advancement happens in-place. As an event enters the machine, elapsed business minutes between $(t_{\text{prev}}, t_{\text{curr}}]$ are calculated immediately using analytical calendar boundary math and accumulated directly into the ticket’s running counters.
* **Deterministic Single-Pass Streaming:** It never stores intermediate state intervals. It maintains strict $O(1)$ auxiliary space complexity per ticket, converting variable temporal spans directly into scalar integers via closed-form evaluation.
* **Cache Line Locality:** Eliminates intermediate vector/list indirection. The CPU operates purely on primitive timestamps and primitive accumulators within the ticket's active memory block.
