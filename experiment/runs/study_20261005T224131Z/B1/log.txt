#### Why `branch_2` is Discarded
`branch_2` implements a two-pass event sweep that dynamically reconstructs running intervals before scanning each interval to compute business minutes:
- **Allocation Churn & Cache Thrashing:** Rebuilding interval lists per ticket forces intermediate object allocation onto the heap ($O(K)$ allocations where $K$ is the number of state transitions). Under enterprise-grade event streams, this incurs severe GC pressure and high cache-miss rates.
- **Redundant Iteration ($O(K)$ Scan Phase):** After paying the memory cost to materialize the interval structures, `branch_2` traverses them a second time to calculate business-minute overlaps. This multi-pass design creates unnecessary serialization bottlenecks when processing high-cardinality ticket batches.

#### Why `branch_1` Wins

- **Single-Pass Stream Processing ($O(1)$ per Event):** State transitions are evaluated sequentially in place. As an event arrives, elapsed business time is folded directly into running counters.
- **Scale Invariance:** Because duration calculations do not scale linearly with temporal span or intermediate interval count, `branch_1` maintains predictable latency profiles whether an SLA window spans ten minutes or six months across multiple holiday boundaries.
