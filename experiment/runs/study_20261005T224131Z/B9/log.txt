While both branches completed test suites cleanly with an exit code of `0` and a reported duration of `0.0s`, raw microbenchmark execution time at small test volumes hides critical algorithmic divergence.

#### 1. Why `branch_2` Fails Architectural Scrutiny
`branch_2` opts for an intermediate event-sweep model:
1. It ingests the raw transition log.
2. It allocates memory to reconstruct discrete active/paused interval tuples.
3. It performs a secondary sweep over those materialized intervals to calculate business-minute overlaps.

This is an anti-pattern for streaming ticket lifecycles. Materializing intermediate interval collections introduces unnecessary heap allocations ($O(K)$ space per ticket, where $K$ is the number of state transitions), burns CPU cache locality, and subjects high-throughput event buses to unnecessary garbage collection or allocator churn. At enterprise scale (millions of ticket updates), this two-pass accumulation approach degrades predictably into latency spikes and memory bloat.

#### 2. Why `branch_1` Survives
`branch_1` implements an inline, per-ticket finite state machine (FSM) that advances ticket lifecycles using closed-form business-minute arithmetic:
* **$O(1)$ Auxiliary Memory:** Ticket states are updated in-place without buffering synthetic interval objects.
* **Single-Pass Evaluation:** When a state transition occurs, elapsed business time is resolved instantaneously via calendar boundary math rather than discrete slice accumulation.
* **Streaming-Ready:** It can process updates incrementally in real time as events arrive, rather than requiring full-history interval reconstruction.

### Final Order
Merge **`branch_1`**. Scythe **`branch_2`**. Closed-form streaming arithmetic beats multi-pass interval materialization every single time.
