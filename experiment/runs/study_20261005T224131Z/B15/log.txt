### Ruthless Synthesis & Architectural Breakdown

#### Rejected: `branch_2` (Event Sweep + Interval Rebuilding + Business Minute Counting)
* **The Flaw:** `branch_2` relies on an intermediate event-sweep phase that materializes ticket interval objects in memory before executing an iterative business-minute counting pass over each segment.
* **Failure Mode at Scale:** 
  1. **Heap Allocation Churn:** Deconstructing transitions into discrete interval sets incurs an $O(E)$ memory penalty, where $E$ is the number of ticket lifecycle events. Under high ticket volumes or frequent status oscillations (e.g., automated ping-pong between `PENDING` and `IN_PROGRESS`), allocation and GC pressure will degrade throughput.
  2. **Computational Redundancy:** Iterating through intervals and accumulating business minutes piecewise reduces SLA tracking to numerical integration of calendar spans. It introduces unnecessary branching per calendar boundary and scales poorly over long-lived tickets spanning weeks or months.

#### Victor: `branch_1` (Per-Ticket State Machine with Closed-Form Business-Minute Arithmetic)
* **The Advantage:** `branch_1` models ticket lifecycle transitions inline as a deterministic state machine and resolves time-in-state via closed-form arithmetic.
* **Why It Survives:**
  1. **$O(1)$ In-Flight Ingestion:** Updates execute in strictly bounded time per transition. State does not need to be buffered, sorted, or transformed into intermediate interval lists.
  2. **Mathematical Precision Without Iteration:** By calculating calendar offsets, work-week multiples, and shift windows algebraically, it eliminates the CPU cycles squandered on interval counting. 
  3. **Zero Allocation Footprint:** Ticket states can be evaluated in-place or streamed through an event bus with negligible heap footprint.
