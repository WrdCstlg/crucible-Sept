### Why `branch_2` Fails Architectural Graduation

`branch_2` implements an **event sweep that rebuilds each ticket's running intervals, then counts business minutes per interval**.

1. **Unnecessary Allocation & Cache Thrashing:** Rebuilding explicit time intervals forces dynamic memory allocation to materialize temporal segments `[start, end)` into heap buffers before business logic is evaluated. In a high-throughput event pipeline, this generates garbage collector pressure, fragmenting the heap and blowing out L1/L2 data cache lines.
2. **Double-Pass Overhead:** Constructing intervals followed by an integration sweep requires $O(K)$ intermediate storage and a two-phase traversal ($O(K \log K)$ if sorting unsorted event boundaries, or $O(K)$ pass-through to aggregate). 
3. **Dead-End Scaling:** While running in `0.0s` against minimal batch fixtures, interval materialization degrades severely when processing millions of tickets subjected to repeated pause/resume lifecycle noise.

---

### Why `branch_1` Survives as the Absolute Winner

`branch_1` implements a **per-ticket state machine that advances each ticket with closed-form business-minute arithmetic**.

1. **Zero-Allocation Stream Processing:** The state machine advances monotonically per event. The computation is executed inline using closed-form calendrical arithmetic ($O(1)$ time complexity per state update) without allocating intermediate collections or interval tuples.
2. **Deterministic Memory Footprint:** Ticket states remain compact, fixed-size structures residing comfortably within a single cache line. Transitions directly accumulate elapsed business minutes and update state markers without materializing intermediate history.
3. **Production Robustness:** Closed-form math avoids the edge-case interval-slicing bugs inherent in temporal sweeps (boundary overlaps, zero-width intervals, leap-second anomalies) and provides steady-state latency profiles under high load.

---
