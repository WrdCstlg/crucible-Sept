# Study results: does a cheaper model inside Crucible beat a stronger model working alone?

**Short answer, for this problem and these models: no.** The cheap model inside Crucible (arm B) did not beat the
strong model alone (arm C), and it did not beat the cheap model alone (arm A) either. The problem turned out to be
too easy to separate the arms: the cheap model alone scored 29/30. What Crucible did show, out of sample, is the
thing it was built for: it automatically caught and quarantined the **7 of 18 (39%)** AI-written test suites that
encoded wrong answers, and it admitted no weak suite.

## 1. The run

- **Pre-registration:** sha256 `428a412cd7ba…`, committed in `7c9587e` before launch; the harness refuses a live run otherwise.
- **Problem:** `experiment/bizsla` (business-hours SLA), frozen; 225 hidden cases, all-or-nothing scoring.
- **Sandbox:** Docker, for every model-written line of code.
- **Planned and completed:** 80 of 80 runs (A 30, B 20, C 30); no run cut by the cap; **0 harness errors**, so nothing was excluded and the integrity rule (§6) was not triggered.
- **Spend:** $27.37 of a $100 hard cap.

|---|---|---|---|---|---|---|
| A: gemini-3.8-flash, 1 call | 30 | 30 (0) | 29 | 97% (83%-99%) | 222.5 | $4.50 |

- **H1 (primary), B vs C:** no detectable difference (p = 0.155).
- **H2, B vs A:** no detectable difference (p = 0.556).
- **H3, Crucible's verdict vs the hidden grader:** 38 candidates, 36 promoted, 2 promoted but failing hidden, 0 rejected but passing hidden. False promotion 2/36, Wilson 95% 1.5%–18.1%.
- **H4, the mutation gate out of sample:** 18 suites, 11 admitted, 0 false security, 0 lost signal, agreement 18/18 (Wilson 95% 82.4%–100%). **Criterion met.**

The recorded file also says "gaps under ~100% could not be detected". **That sentence is wrong**; see Deviation 1. The
corrected statement, in the words §4 requires: **a null result does not show the arms are equivalent. With these n,
a B rate at or below about 74% (26 points under C's 100%) would have been detected with 80% power; smaller gaps
could not be.**

## 3. What the results mean

### H1 and H2: the main question

- **Crucible gave the cheaper model no measurable accuracy gain on this problem.** B (90%) was numerically below both A (97%) and C (100%), and neither gap is significant.
- **The arms hit a ceiling.** The problem was chosen to be hard, and the cheap model alone still solved 29 of 30. With every arm near 100%, there was little room for a process to add anything. The honest reading is "no effect detectable here", not "the process does not help".
- **Both of B's failures were infrastructure hangs, not wrong code.** B11 and B20 each hit the 45-minute run limit while waiting on a single model API call that never returned (there was no client-side request timeout). The pre-registration counts timeouts as failures, and they are counted. In B20 both candidates had already been written and both pass all 225 hidden cases; the run hung before Crucible issued its verdict. Every B run that finished passed.
- **Cost:** B cost about the same as C ($8.69 for 20 runs vs $8.36 for 30), roughly 1.6× C per run and 2.9× A per run, with no accuracy gain. On this problem, the cheapest route to a correct answer was the cheap model alone.

### H3: how far Crucible's own verdict can be trusted

- **0 correct candidates were rejected.** Crucible never threw away good code.
- **2 of 36 promoted candidates failed the hidden grader:** B14 round 1 branch 2 (149/225) and B16 round 1 branch 2 (224/225). In both runs the code Crucible finally shipped was a different candidate that passed, so neither false promotion cost a run.
- **Why it happened:** arm B, by design, has no reference solution, so its only decisive ground truth is the 4 worked examples printed in the spec. Every promotion happened in round 1 on those 4 cases alone. A 4-case acceptance set cannot see a bug like B14's. This is the expected cost of running Crucible without real acceptance tests, and it is the main thing a user should take away: **Crucible's verdict is only as strong as the ground truth it is given.**

### H4: does the mutation gate keep tautological AI tests out?

- **The headline problem is real and large:** 7 of 18 AI-written suites (39%, Wilson 95% 20%–61%) contained at least one wrong expectation, and failed against the trusted reference. Any pipeline that trusted those suites would have rejected correct code or, worse, certified code that matches the model's misreading.
- **The gate quarantined all 7** at the baseline step, before any mutant ran.
- **All 11 admitted suites were independently strong:** each caught 18–21 of the 21 planted bugs it never saw. 0 false security.
- **Caveat: this was the easy half of the test.** No suite in this sample was weak but reference-passing, the case the code, output and input axes exist to catch. Those axes admitted 11 strong suites correctly but were never challenged by a weak one out of sample. Their in-sample record, where hand-written weak controls (a tautological suite and a count-only suite) were quarantined by those axes, is in [`gate_validation/REPORT.md`](gate_validation/REPORT.md).
- **Consistent with the pilots:** in-sample, 4 of the 7 recorded AI-written suites also failed against the reference and were quarantined.

## 4. Deviations from the pre-registration

1. **Reporting bug in the power statement (fixed after the run).** `stats.min_detectable_gap` searched only upward from the comparison arm's rate. With C at 100% there was no room upward, so it returned 1.0 and `RESULTS.md` printed "gaps under ~100%". The p-values, rates and intervals are unaffected. The function now searches toward the side with room ([`stats.py`](stats.py)), with regression tests in [`tests/test_stats.py`](../tests/test_stats.py) and [`tests/test_study.py`](../tests/test_study.py). Re-running the pre-registered analysis on the recorded `summary.json` with the fixed code reproduces every tally and p-value exactly and changes only the power sentence:
   - H1: gaps under ~26% (B below C's 100%) could not be detected at 80% power.
   - H2: gaps under ~30% (B below A's 97%) could not be detected at 80% power.
2. **Request timeout added after the run, for future runs only.** The two B timeouts were API calls with no client timeout. [`rig/providers.py`](rig/providers.py) now accepts `settings.request_timeout_s` or `CRUCIBLE_REQUEST_TIMEOUT_S` (off by default, so the recorded configuration replays unchanged), tested in [`tests/test_providers.py`](../tests/test_providers.py). This changes no result here.
3. **Hand-case review.** §9 says the author reviews the 20 hand-derived cases before the live run. No written sign-off of that review is stored in the repository. No case was changed: the per-file hashes recorded in `config.json` at launch match `bizsla/FROZEN.json`, whose sha256 is the pre-registered `39c19fed…`.

## 5. Exploratory analyses (not pre-registered; do not treat as confirmatory)

- **B on completed runs only:** 18/18 vs C 30/30, Fisher p = 1.0. If the two API hangs are set aside, B and C are indistinguishable.
- **A vs C:** 29/30 vs 30/30, p = 1.0. At n = 30/30, an A rate at or below about 74% would have been detected with 80% power.

## 6. Limits

- **One problem, two models.** Nothing here generalises beyond `bizsla`, gemini-3.8-flash and claude-opus-5-5.
- **Ceiling effect.** The problem did not separate the arms. A fair test of "process beats model" needs a problem the cheap model fails alone most of the time.
- **Who wrote the ground truth.** The spec, both oracles, the hand cases and the planted bugs were drafted by Claude (via Antigravity) under the author's direction. Arm C is also a Claude model, so any shared misreading biases the result toward C. Arm C scored 30/30, which is consistent with either a strong model or that bias; this study cannot tell them apart.
- **B's acceptance set was 4 cases.** This is by design (information parity), and H3 shows its cost.
- **H4 did not exercise the weak-but-passing case** out of sample (see §3).
